# UI 自动化测试用例转换 Prompt

## 目标说明

将功能测试用例转换为适合 UI 自动化的测试用例。转换后的用例需满足：
- 步骤操作可被 Midscene AI 直接执行（aiTap/aiInput/aiAssert）
- 元素描述清晰，包含类型、视觉特征和位置上下文
- 聚焦可在浏览器/应用中可见、可交互的行为
- 排除无法自动化的步骤（如"检查数据库"、"联系运营"等）

## 输入格式

源用例使用 `[源用例]` 标签包裹，YAML 格式：

```
[源用例]
<此处粘贴功能测试用例 YAML 内容>
[/源用例]
```

---

## STEP_FORMAT_GUIDE：步骤格式规范

以下是 UI 自动化测试步骤的标准格式，每种操作类型对应固定句式：

| 操作类型 | 句式模板 | 示例 |
|---------|---------|------|
| 点击操作 | 点击[目标元素] | 点击顶部导航栏的「发送」按钮 |
| 输入操作 | 在[目标输入框]中输入[具体值] | 在消息输入框中输入"你好，AI助手" |
| 滚动操作 | 向[方向]滚动[目标区域] | 向下滚动消息列表区域 |
| 按键操作 | 按下[按键名] | 按下 Enter 键 |
| 悬停操作 | 悬停在[目标元素] | 悬停在用户头像上 |
| 等待操作 | 等待[N]秒 | 等待3秒 |
| 导航操作 | 跳转到[URL] | 跳转到 /chat 页面 |

---

## 元素描述最佳实践

描述 UI 元素时，需包含以下三个维度：

1. **元素类型**：按钮 / 输入框 / 链接 / 图标 / 文本 / 下拉框 / 复选框 / 单选框
2. **视觉特征**：颜色、文字标签、图标名称（如"发送"图标、蓝色确认按钮）
3. **位置上下文**：相对位置（"位于输入框右侧"）或区域归属（"顶部导航栏"、"左侧侧边栏"）

### 示例对比

**✅ 好的元素描述：**
- "点击消息输入框右下角的蓝色「发送」按钮"
- "点击顶部导航栏中的「新建对话」图标按钮"
- "在左侧对话列表顶部的搜索输入框中输入关键词"
- "点击消息气泡右上角出现的「复制」图标"

**❌ 差的元素描述：**
- "点击发送"（缺少位置上下文和元素类型）
- "找到输入框输入文字"（没有具体值，操作不明确）
- "点击按钮"（没有任何可识别特征）
- "检查界面上是否有提示"（断言描述模糊）

## 转换规则

### 规则 1：保留核心流程（P0/P1）
- **保留**：P0（冒烟级）和 P1（核心场景）用例
- **过滤**：P2 及以下的边界值测试、极端异常场景、低频操作

### 规则 2：减少边界值和异常场景
- 只保留**用户常见的异常路径**（如"输入框为空时点击提交"、"网络断开时的提示"）
- 移除数字精确边界（如"输入 255 个字符"）、后端校验类测试

### 规则 3：步骤标准化
- 所有步骤必须使用 STEP_FORMAT_GUIDE 中的标准句式
- 每步骤只包含一个原子操作（一次点击、一次输入等）
- 步骤总数控制在 **3～10 步**，超出时拆分为多个用例

### 规则 4：移除不可自动化步骤
以下类型的步骤必须移除或替换为可验证的 UI 断言：
- 查询数据库 / 调用后台接口验证
- 手动联系客服 / 运营操作
- 需要物理设备操作（如扫码、NFC）
- 依赖第三方系统回调无法模拟的步骤
- "等待人工审核"等异步人工介入

### 规则 5：添加元素上下文
- 将功能测试中抽象的"点击发送"改写为包含位置和视觉特征的完整描述
- 预期结果中需包含**可在 UI 中验证的可见状态**（文字出现、弹窗显示、跳转发生等）

## 输出格式（YAML 结构）

```yaml
metadata:
  source_module: <模块名>
  generated_at: <日期>
  total: <用例总数>
  platform: web
  note: "由功能测试用例转换，保留 P0/P1，适用于 Midscene AI 自动化"

cases:
  - id: UI-<模块缩写>-001
    title: <简洁的用例标题>
    priority: P0   # P0 或 P1
    platform: web
    source_testcase: <对应的源功能用例 ID，如 TC-001>
    preconditions:
      - <前置条件1，描述页面状态或登录状态>
      - <前置条件2>
    steps:
      - step: 1
        action: "<使用 STEP_FORMAT_GUIDE 标准句式>"
      - step: 2
        action: "<操作描述>"
      - step: 3
        action: "<操作描述>"
    expected:
      - "<可在 UI 中观察到的预期结果1>"
      - "<可在 UI 中观察到的预期结果2>"
    tags:
      - smoke       # P0 用例添加 smoke 标签
      - <功能标签，如 chat、login、navigation>
    metadata:
      automation_note: "<特殊说明，如需要等待时间、弹窗处理等>"
```

## 转换示例

### 输入（功能测试用例片段）

```yaml
cases:
  - id: TC-CHAT-003
    title: 用户发送文本消息
    priority: P0
    steps:
      - 打开应用，进入对话页面
      - 在消息输入框中点击
      - 输入"测试消息内容"
      - 检查数据库 message 表是否有新记录（条件：字符数 < 2000）
      - 点击发送按钮
      - 等待 AI 回复
    expected:
      - 消息发送成功
      - 消息气泡显示在对话列表中
      - AI 返回回复内容
      - 数据库记录正确写入
```

### 输出（UI 自动化测试用例）

```yaml
cases:
  - id: UI-CHAT-001
    title: 发送文本消息并收到 AI 回复
    priority: P0
    platform: web
    source_testcase: TC-CHAT-003
    preconditions:
      - 用户已登录
      - 当前页面为对话页面
    steps:
      - step: 1
        action: "点击页面中央的消息输入框"
      - step: 2
        action: "在消息输入框中输入\"测试消息内容\""
      - step: 3
        action: "点击输入框右下角的蓝色「发送」按钮"
      - step: 4
        action: "等待5秒"
    expected:
      - "输入的消息气泡出现在对话列表底部"
      - "消息气泡显示\"测试消息内容\"文字"
      - "对话列表中出现 AI 回复的消息气泡"
    tags:
      - smoke
      - chat
    metadata:
      automation_note: "等待 AI 回复时间根据网络情况可能需要调整"
```

> 注意：原功能用例中"检查数据库"和"数据库记录正确写入"步骤已被移除，因无法通过 UI 自动化验证。

---

## 输出要求

1. **直接输出 YAML**，不需要额外解释或 Markdown 包裹
2. 使用 **2 空格缩进**
3. 字符串值使用**双引号**
4. `id` 格式：`UI-<模块缩写大写>-<三位序号>`，如 `UI-CHAT-001`
5. 每个用例的 `steps` 数量控制在 3～10 步
6. `expected` 每条描述需具体可观测，不得出现"验证数据库"、"检查后台"等不可 UI 验证的内容
7. 输出的用例总数通常为源用例的 **40%～70%**（因过滤了不适合自动化的用例）
