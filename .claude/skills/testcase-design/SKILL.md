# /testcase-design — 测试用例生成

## 触发场景
用户运行 `/testcase-design` 或提到"生成测试用例"、"为某模块写用例"时激活。

## 配置读取
启动时执行以下操作：
1. 用 `Bash` 运行 `pwd` 获取工作目录，记为 `$WORKDIR`，后续所有文件路径均拼接为绝对路径（如 `$WORKDIR/testing/mindmaps/_drafts/_analysis-<模块>.md`）
2. 读取 `$WORKDIR/.claude/config/testcase-workflow.yml`，获取：
- `project.dev_repo`：开发代码仓库路径
- `project.module_map`：模块名到代码路径的映射
- `project.scan_file_threshold`：预扫描文件数阈值（默认 20，超过则触发子模块选择）
- `experience.path`：经验库路径

## 输入方式

### 直接模式（带参数）
```
/testcase-design --module <模块名>
/testcase-design --code <代码路径>
/testcase-design --prd <PRD路径>
/testcase-design --code <路径> --prd <PRD路径>
/testcase-design --module <模块名> --with-experience
```

### 交互模式（无参数）
无参数时进入交互引导：

```
请选择输入方式：
  [1] 从模块名生成（推荐）—— AI 自动定位代码
  [2] 从代码路径生成 —— 精确控制范围
  [3] 从 PRD 文档生成 —— 有需求文档时用
  [4] 组合输入（代码 + PRD）—— 质量最高
```

**步骤 2：选择具体模块/路径**

根据步骤 1 的选择，用 `AskUserQuestion` 询问具体目标：
- 选 [1]（模块名）：从 `module_map` 读取并展示编号列表
  - **只列出 `testable` 字段不为 `false` 的模块，`testable: false` 的模块不得出现在列表中**
  - 按 module_map 中 `# ──` 分组标题分组，每组之间空一行
  - 格式：编号 + 模块名 + 该条目上方注释的第一句；若模块有 `priority: P0` 则在模块名后加 `[P0]`
  - 最后一项为手动输入
  ```

    [3]  chat-ui [P0]       — 界面渲染（消息块、Markdown、交互提示、导航）

  ── 内容与知识 ──
    [7]  knowledge-library — 文档上传、检索、知识片段管理
    [8]  memory            — 用户记忆条目的增删改查与上下文注入

```

```
  [y] 是
  [n] 否
```

最后输出配置确认，再开始执行。

## testable 检查

在用户确认模块后，读取该模块的 `testable` 字段：
- 若 `testable: false`：立即终止并提示：
  ```
  ⚠️ 模块 <模块名> 为纯逻辑层/后端服务，不适合手工测试用例生成。
  建议由开发工程师编写单元测试/集成测试。
  如需强制生成，请使用 --force 参数。
  ```
  除非用户附加了 `--force`，否则不继续执行。
- 若 `testable` 字段缺失或为 `true`：正常继续。

## 四阶段执行流程

### 阶段 0：预扫描检查（Pre-scan Check）
- 定位目标代码路径（同阶段 1 的定位逻辑）
- 统计目标路径下（含子目录，深度 = scan_depth）的文件数量
- 如果文件数 ≤ 20：直接进入阶段 1
- 如果文件数 > 20：触发子模块选择流程（见下方）

**子模块选择流程（文件数 > 20 时）：**
```
检测到模块 <模块名> 包含 <N> 个文件，超过分析阈值（20），一次性分析可能影响质量。

请选择处理方式：
  [1] 列出子目录，我来选择具体范围（推荐）
  [2] 输入更精确的子路径
  [3] 忽略阈值，继续全量分析（不推荐，质量可能下降）
```

选 [1] 时：列出目标路径下的一级子目录及各自文件数，供用户选择一个或多个。
选 [2] 时：提示用户输入相对于 dev_repo 的子路径，重新统计文件数。
选 [3] 时：记录警告"⚠️ 全量分析，文件数 <N>，分析质量可能下降"，继续阶段 1。

选定范围后，将实际扫描路径更新为用户选择的子路径，继续阶段 1。

### 阶段 1：代码理解（Code Comprehension）
- 根据输入方式定位代码：
  - `--module`：查 `module_map` 找路径，在 `dev_repo` 下读取；若该模块有 `ui_entry` 字段，额外读取该文件作为 UI 入口，优先从中提取用户可见的操作路径和交互行为；若有 `scan_filter` 字段（如 `*.tsx`），扫描时只读取匹配该 glob 的文件，忽略其余文件
  - `--code`：直接读取指定路径（相对于 `dev_repo`）
  - `--prd`：读取 PRD 文档（无代码时跳过代码读取）
  - 组合：同时读取代码和 PRD
- 分析内容：
  - 识别功能点和业务逻辑
  - 提取输入参数、输出结果、状态转换
  - 识别风险点（无错误处理、复杂条件分支、外部依赖等）
  - 标注关联代码文件和置信度（high/medium/low）
- 输出：`testing/mindmaps/_drafts/_analysis-<模块>.md`

_analysis 文件格式：
```
# <模块> 功能分析

## 功能点清单
| 功能点 | 描述 | 输入 | 输出 | 风险等级 |
|--------|------|------|------|---------|

## 状态转换
（如有状态机，列出状态和转换条件）

## 风险点
- 风险描述（代码位置）

## 关联代码
- path [confidence: high/medium/low, by: ai]

## 历史 Bug 参考
（如有同模块历史 bug，列出 ID 和标题；无则省略此节）
- BUG-XXXX：<标题>
```

### 阶段 2：测试分析与建模（Test Analysis & Modeling）

基于阶段 1 的 `_analysis-<模块>.md`，执行以下步骤：

**Step 1：测试点四分类**

扫描功能点清单，将每个测试点归入四类（分类规则见 `references/methodology.md` 第一节）：
- 流程类：有步骤分支，可绘流程图
- 参数类：参数值有限，不同值不同处理
- 数据类：取值范围，范围内处理相同
- 组合类：多因素叠加影响结果

**Step 2：按类型建模**

- 流程类 → 用 Mermaid 绘制流程图或状态机图
- 参数类 → 建输入-输出表
- 数据类 → 建等价类分析表（有效等价类 + 无效等价类）
- 组合类 → 建因子表

**Step 3：风险等级标注**

每个测试点标注风险等级（高/中/低）：
- 高：复杂逻辑、历史 bug 多、影响核心流程、需求描述模糊
- 中：有一定复杂度、有已知边界问题
- 低：逻辑简单、已稳定运行的旧功能

**Step 4：测试标签标注**

根据测试点特征标注专项测试标签（可多选）：
- 接口测试：涉及 API 调用
- 性能测试：大数据量、高并发
- 安全测试：涉及登录/权限/用户输入
- 并发测试：共享资源、同时操作
- 兼容性测试：多端/多浏览器

**Step 5：更新 _analysis 文件**

将分类结果、模型、风险等级、测试标签追加到 `testing/mindmaps/_drafts/_analysis-<模块>.md`：

```
## 测试点分类与建模

| 编号 | 测试点 | 类型 | 风险 | 测试标签 |
|------|--------|------|------|---------|
| TP01 | <描述> | 流程类 | 高 | 安全测试 |

### 流程图（流程类测试点）
（Mermaid 图）

### 等价类分析表（数据类测试点）
| 条件 | 有效等价类 | 无效等价类 |
|------|-----------|-----------|
```

### 阶段 3：测试设计（Test Design）
- 基于阶段 1 的 _analysis.md
- 如果 `--with-experience`，读取 `testing/experience.md`，参考历史漏测场景和模板
- 读取 `bugs/snapshots/index.yml`（如存在），筛选同模块的历史 bug（含 open/closed/reopened 状态）
  - 将历史 bug 的标题和 verify_note 作为"已知风险点"参考，优先为其生成回归测试用例
  - 在 _design-<模块>.md 中增加"历史 Bug 参考"节，列出参考的 bug ID 和标题
  - 如果 `bugs/snapshots/` 不存在或该模块无历史 bug，跳过此步骤
- 按 6 维度列出测试点草稿（维度定义和隐式方法论见 `references/methodology.md`）
- 每个测试点标注优先级（P0/P1/P2）和平台（desktop/web/mobile）
- 路径覆盖策略按风险等级选择（规则见 `references/methodology.md` 第二节 2.2）：
  - 风险"高" → 全覆盖；风险"中" → 最小线性无关覆盖；风险"低" → 分支覆盖
- 边界值必须精确到具体数字（如"-1、0、1"，不能写"输入负数"）
- 每个测试点继承阶段 2 标注的测试标签，写入用例的"测试标签"列
- 输出：`testing/mindmaps/_drafts/_design-<模块>.md`

### 阶段 4：用例生成（Case Generation）

**输出格式（H1-H6 层级，严禁生成表格）：**

```
H1  <模块名>测试用例
H2  测试维度（正常场景 / 异常场景 / 边界值 / 兼容性 / 性能 / 安全）
H3  功能测试点（来自阶段2测试点分类，如"登录流程"）
H4  验证点（同一测试点下的细分方向，如"凭据正确性校验"）
H5  用例场景（简洁描述，含关键条件；不含优先级标注）
H6  前置条件   ← 固定子节点1
H6  测试步骤   ← 固定子节点2（有序列表）
H6  预期结果   ← 固定子节点3（可验证列表）
```

示例：
```markdown
## 正常场景
### 登录流程
#### 凭据正确性校验
##### 已激活用户使用正确的邮箱和密码登录
###### 前置条件
- 用户已注册并完成邮箱激活
###### 测试步骤
1. 打开登录页面
2. 输入正确的邮箱和密码
3. 点击登录按钮
###### 预期结果
- 登录成功，跳转到主页
- 用户会话正确创建
```

- 优先级（P0/P1/P2）**只写入摘要表**，不出现在 H5 标题中
- 每个 H5 用例必须有 H6 前置条件、H6 测试步骤、H6 预期结果三个子节点
- 将阶段 1 分析的关联代码（含 confidence）写入文件头部 YAML frontmatter
- 输出：`testing/mindmaps/<模块>.md`（草稿，无摘要表）

**写入策略（必须严格遵守）：**
用例文件内容较大，必须分段写入，规则如下：
1. 用 `Write` 工具写入文件头部（YAML frontmatter + H1 标题），仅此一次，格式：
   ```
   ---
   linked_code:
     ai:
       - path: <路径> [confidence: high/medium/low, by: ai]
   ---

   # <模块名>测试用例
   ```
2. 后续所有内容追加，**只能用 `Bash`**，格式：
   ```bash
   cat >> "$WORKDIR/testing/mindmaps/<模块>.md" << 'EOF'
   <内容，不超过 80 行>
   EOF
   ```
3. **严禁用 `Edit` 工具追加内容**（Edit 需要 old_string，不适用于追加）
4. **严禁再次调用 `Write` 覆盖已有内容**
5. 每次 `cat >>` 追加一个 H2 维度下的所有用例，完成后再追加下一个维度

### 阶段 5：量化门禁与摘要（Quality Gate）
按 `references/methodology.md` 第七节自检清单逐项执行：

**量化指标检查：**
对照 `_analysis-<模块>.md` 的测试点清单，逐一映射到已生成的用例：
- 测试点覆盖率 < 95%：列出未覆盖的测试点，补充用例后继续
- 反向/异常用例占比 < 30%：列出缺口数量，补充后继续
- 边界值未精确到具体数字：找出模糊描述，修正后继续
- P0 为 0 或 P0+P1 < 40%：调整优先级后继续

**高危场景检查：**
根据功能类型（Web前端/API后端/移动端）确定适用的高危场景类别，逐类检查：
- 有对应用例：✅
- 无对应用例且适用：补充后标 ✅
- 不适用：标注原因

**门禁通过后**生成测试点摘要表（格式见下方，新增"测试标签"列），注入到 MD 开头。

生成测试点摘要表，注入到 MD 开头（关联代码之后）：
```
## 测试点摘要

| 编号 | 用例标题 | 维度 | 优先级 | 平台 | 测试标签 |
|------|---------|------|--------|------|---------|
| AUTH-??? | 用例标题 | 正常场景 | P0 | desktop,web | 安全测试 |

**统计**：总 N 个 | P0: N | P1: N | P2: N
**维度**：正常 N | 异常 N | 边界 N | 兼容 N | 性能 N | 安全 N
```

输出最终 `testing/mindmaps/<模块>.md`（含摘要表）。
